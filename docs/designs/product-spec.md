# Redeye — Product Spec

**Last updated:** 2026-09-11

## Overview

Redeye is a travel planner app for iPhone. Users create trips, build itineraries (with or without AI help), and use maps to navigate activities while traveling. The app works offline for previously loaded trips and respects user privacy around location data.

**Target users:** The creator and a small group of friends. The app does not need to support large-scale public use for MVP, but should be a real, polished, downloadable app — not a prototype.

---

## Core Concepts

### Trip
A trip is the top-level object. It represents a single journey to a destination.

A trip has:
- A title (user-defined, e.g. "Tokyo Spring 2026")
- A destination (city or region)
- A start date and end date
- A mode: **structured** or **unstructured** (chosen at creation, can be changed later)
- An optional home base (hotel name and/or address)
- An optional set of preferences/interests (e.g. "food-focused," "art museums," "nightlife," "budget-friendly")
- A status: active or archived

A user can have multiple saved trips. Trips can be created, edited, archived, and deleted.

### Activity
An activity is a single thing to do or see — a restaurant, a museum, a park, a shop, a neighborhood walk, a show. Activities belong to a trip.

An activity has:
- A name
- An optional description or notes
- A category (e.g. restaurant, attraction, shopping, museum, nightlife, other)
- A location (coordinates and/or address)
- An optional area/neighborhood label
- A status: planned, visited, or skipped
- A source: added manually by the user, generated by AI, or found via search

In structured mode, activities also have:
- A day assignment
- A start time and end time (or estimated duration)
- An order within the day

In unstructured mode, activities have:
- An order within their group (grouped by area and/or category)

## Functional Requirements

### FR-1: Trip Management

**FR-1.1** The user can create a new trip by providing a destination and dates. Mode selection (structured or unstructured) happens at creation.

**FR-1.2** The user can view a list of all their trips, separated by active and archived.

**FR-1.3** The user can edit any trip's details (title, destination, dates, home base, preferences, mode).

**FR-1.4** The user can archive a trip. Archived trips remain viewable but are visually separated from active trips.

**FR-1.5** The user can delete a trip permanently. This should require confirmation.

**FR-1.6** The user can switch a trip between structured and unstructured mode. When switching from structured to unstructured, day assignments and times are removed but activities are preserved. When switching from unstructured to structured, activities are preserved without day assignments and the user can assign them.

### FR-2: Structured Mode (Day-by-Day Itinerary)

**FR-2.1** The trip view shows a day-by-day breakdown based on the trip's date range (e.g. Day 1 — Sept 15, Day 2 — Sept 16).

**FR-2.2** Each day shows its activities in chronological order by start time.

**FR-2.3** The user can add an activity to a specific day, specifying a start time and either an end time or estimated duration.

**FR-2.4** The user can reorder activities within a day (drag to rearrange).

**FR-2.5** The user can move an activity from one day to another.

**FR-2.6** The user can remove an activity from a day without deleting it (moves it to an "unassigned" holding area for the trip).

**FR-2.7** If the trip dates change, days are added or removed accordingly. Activities on removed days move to unassigned.

### FR-3: Unstructured Mode (Categorized List)

**FR-3.1** The trip view shows activities grouped by area/neighborhood (e.g. "Shibuya," "Shinjuku," "Downtown").

**FR-3.2** Within each area, activities can optionally be sub-grouped by category (restaurants, attractions, shopping, etc.).

**FR-3.3** The user can add an activity with an area label and category.

**FR-3.4** The user can reorder activities within a group.

**FR-3.5** The user can move an activity to a different area or category.

**FR-3.6** The user can view all activities as a flat list (ignoring grouping) if they prefer.

### FR-4: AI Itinerary Generation

**FR-4.1** From any trip, the user can request an AI-generated itinerary. The generation uses the trip's destination, dates, preferences, and mode.

**FR-4.2** For structured mode, the AI generates a day-by-day itinerary with timed activities, covering the full date range.

**FR-4.3** For unstructured mode, the AI generates a categorized list of recommended activities, organized by area and category.

**FR-4.4** While generating, the user sees a loading/progress state. Activities appear progressively as they are generated (not all at once after a long wait).

**FR-4.5** After generation, the user can review the suggested itinerary before accepting it. They can accept all, accept selectively, or discard.

**FR-4.6** Accepted AI-generated activities are fully editable — the user can modify, reorder, or delete them just like manually added activities.

**FR-4.7** The user can re-generate an itinerary for a trip at any time. They should be warned that this will replace AI-generated activities (manually added ones are preserved).

**FR-4.8** AI suggestions should include a mix of well-known highlights and lesser-known local spots, tailored to the user's stated preferences.

### FR-5: Activity Search & Discovery

**FR-5.1** The user can search for activities to add to a trip. Search should accept a text query (e.g. "ramen near Shinjuku") and return relevant results.

**FR-5.2** Search results show the activity name, category, location, and a brief description or rating where available.

**FR-5.3** The user can add a search result directly to their trip (assigning it to a day in structured mode, or a group in unstructured mode).

**FR-5.4** Suggestions of popular/recommended activities for the trip's destination should be available without requiring a search query (browsable discovery).

### FR-6: Maps

**FR-6.1** The user can view a map showing all saved activities for a trip as pins.

**FR-6.2** Pins are visually distinguished by category (e.g. different colors or icons for restaurants vs. attractions).

**FR-6.3** Tapping a pin opens a summary of the activity (name, category, time if assigned, notes).

**FR-6.4** From an activity's summary, the user can open directions in Apple Maps or Google Maps.

**FR-6.5** The map shows the user's current location (when location permission is granted and the user is viewing the map).

**FR-6.6** The user can view nearby saved activities sorted by distance from their current location. "Nearby" should have a reasonable default radius (e.g. 1 km) and be adjustable.

**FR-6.7** In structured mode, the map can filter to show only activities for a specific day.

**FR-6.8** The home base (hotel) is shown on the map with a distinct marker.

### FR-7: On-Trip Experience

**FR-7.1** When the user is within the trip's date range, the app surfaces relevant information: today's activities (structured mode) or nearby activities (both modes).

**FR-7.2** The user can mark activities as "visited" or "skipped" to track progress.

**FR-7.3** The user can add new activities on the fly while traveling (quick-add with minimal required fields).

### FR-8: Route Planning (Stretch Goal)

**FR-8.1** For a given day (structured mode), the user can generate an optimized walking/transit route that visits all activities in an efficient order.

**FR-8.2** The route is shown on the map with a path connecting activities.

**FR-8.3** The user can adjust the route by reordering stops, and the path updates accordingly.

## Non-Functional Requirements

### NFR-1: Performance

**NFR-1.1** Loading the trip list: under 1 second.

**NFR-1.2** Loading a trip's itinerary and activities: under 1 second.

**NFR-1.3** AI itinerary generation: under 1 minute for a full trip. Progressive results should begin appearing within a few seconds.

**NFR-1.4** Activity search results: under 1 second.

**NFR-1.5** Map rendering with activity pins: under 2 seconds.

**NFR-1.6** App launch to usable state: under 2 seconds.

### NFR-2: Offline Support

**NFR-2.1** Previously loaded trip itineraries and saved activities must remain viewable without internet access.

**NFR-2.2** The user can edit trips and activities while offline. Changes are saved locally and synced when connectivity returns.

**NFR-2.3** Map tiles for previously viewed areas should be available offline (to the extent the mapping platform supports caching).

**NFR-2.4** AI generation and activity search require internet and should show a clear message when unavailable.

**NFR-2.5** The app should clearly indicate when it is operating offline (subtle, non-intrusive indicator).

### NFR-3: Data Integrity

**NFR-3.1** Saved trip changes must not be lost if the app is closed, crashes, or the network request fails.

**NFR-3.2** If a sync conflict occurs (e.g. edited on two devices), the most recent change wins. No silent data loss.

**NFR-3.3** Deleting a trip is permanent and irreversible — the confirmation dialog should make this clear.

### NFR-4: Privacy & Location

**NFR-4.1** Location permission is requested only when the user takes an action that needs it (e.g. opening the map, viewing nearby activities). Not on app launch.

**NFR-4.2** The app does not continuously track the user's location. Location is checked on demand (when the user views the map or requests nearby activities).

**NFR-4.3** Location data is not persisted or sent to any server. It is used only on-device to calculate distances and display the user's position on the map.

**NFR-4.4** The app must remain fully functional if location access is denied. Location-dependent features (nearby sorting, current location on map) are gracefully hidden or show an explanatory message.

### NFR-5: Distribution

**NFR-5.1** The app must be installable on a real iPhone — not a web app or PWA.

**NFR-5.2** The app should be distributable to a small group of friends via TestFlight.

**NFR-5.3** The app should support iOS 17 and above.

### NFR-6: Usability

**NFR-6.1** The app should be usable one-handed on an iPhone (primary actions reachable with thumb).

**NFR-6.2** Text should be legible and controls should be large enough for comfortable use while walking.

**NFR-6.3** The app should support both light and dark mode.

**NFR-6.4** The app should support Dynamic Type (system font size preferences).

## Out of Scope for MVP

These are explicitly not part of the first version:

- Multi-user collaboration on a single trip (sharing a trip with friends for co-editing)
- Social features (sharing trips publicly, following other travelers)
- Booking integration (hotels, flights, restaurants)
- Budget tracking or expense splitting
- Photo/media attachments on activities
- Calendar integration (syncing itinerary to iOS Calendar)
- Push notifications or reminders
- Android support
- Web app
- Multiple language support
